# Factory

A production line for Claude Code. You hand it a spec, approve the task list, and
it runs a board of agents that cannot mark work done until a gate proves it —
while a live dashboard tells you what the team is doing, what it is stuck on, and
what it needs from you.

```
🏭 C2-kasa-akisi 3/7 ▶2 ✋1 ⛔1 ⚠1
   change      done  agents questions blocked stalled
```

## Install

```bash
claude plugin marketplace add yunusemrealpak/claude-factory
claude plugin install factory@claude-factory
```

Then, in any project:

```
/factory:init <spec file, or a sentence describing the work>
```

It reads the codebase, proposes a task list and a quality gate, and waits for your
approval. Nothing is built until you say yes. Then:

```
/factory:run
```

That builds the approved board as a workflow: one deterministic preflight, then one
builder, one check and one settle per task, and one full check at the end (see
[the loop](#the-loop)). `/factory:fast` is its old name and still works for one
release.

## What it actually does

**A board with one law.** Tasks live in `tasks/backlog|in-progress|blocked|done`.
A task reaches `done` only after `gates/verify.sh <id>` wrote its verified marker.
That law is enforced by a `PreToolUse` hook, not by asking an agent nicely: a move
without the marker is denied.

**A gate that is hard to fool.** The gate runs build, tests, architecture rules and
lint, and it also counts: a suite that ran zero tests is not green, a task that
deleted a test file or added a skip marker (compared with HEAD) is not green, and an
acceptance criterion whose only evidence is a sentence in a markdown file is
rejected outright. It fingerprints failures, so a task that fails twice on the
identical error is stopped rather than retried until its budget runs out.

**One commit per task, locally.** When a task's check is green, `factory-settle`
lands it: `factory-land` commits exactly the files the task listed, with
`Factory-Task` and `Factory-Change` trailers. An agent never pushes (a script publishes only when the autonomy level you consented to allows it), and your own uncommitted work is never swept in.
When every task of a change is done, the change is archived with a summary and a
local ref under `refs/factory/`.

**A team you can watch.** Hooks write an event log; from it, `.factory/dashboard.html`
shows what is running, what is struggling, what is waiting for you, how long tasks
take and what the session has cost. It costs zero model turns — every byte of it is
generated by shell scripts from files on disk.

**A way to ask you things.** When a task needs a decision only you can make - it
is marked `needs_human`, it does not lint, or it cannot be built as written - the
run blocks it and puts one question in your inbox (`factory-ask list`) instead of
going quiet in `blocked`. The question lands on the dashboard and raises a desktop
notification; the run carries on with the rest of the board while it waits, and the
next `/factory:run` takes your answer back into the task.

**Speed as a constraint.** A reviewer is sent only to a task marked
`review: always` or one that touches a path in `risk_paths`, and only for what a
check cannot judge: findings about lint, style or compiler output are dropped
before they count. A red check gets a fresh builder, not a reviewer. What happens
to each task, the ready set and the task lint are scripts, not model reasoning.

## The loop

`/factory:run` builds the approved board without a model in the loop between
tasks. It makes two calls: `factory-preflight` settles the board on disk and
prints the plan, then a Claude Code workflow, `factory:loop`, runs it. The
dependency graph, the scheduling, the retries and the review routing are plain
JavaScript, and what happens to each task is decided by scripts from what is on
disk, so the only model work left is writing each task's code.

Leave the run alone while it works. A Monitor or a poll on it wakes the main
session once per builder, and every wake-up re-reads that session's whole
context: on a 14-task run that was about a quarter of its cost. The workflow
reports once, at the end.

- **One builder per task.** It starts the task (`factory-start` prints the task
  and its lessons in one go), writes the code and the tests the task asks for,
  and does not run tests while it works. Its last command is `factory-settle`.
- **One deterministic check.** `factory-check` formats the touched files, builds
  and lints, runs the tests of the units the change reaches - the parts the
  project is made of and their dependents, declared in the config - and runs
  the task's own acceptance command. It knows no language: every command comes
  from the project. It keeps every guard of the gate: marker, zero tests,
  self-certifying acceptance, NO PROGRESS, and a test census judged per task
  against HEAD, so tasks in flight cannot trip each other.
- **Settle, then judge the whole once.** `factory-settle` decides from disk what
  happens to a task - land it, send it to review, let it wait, retry it, block it -
  and prints one line saying which; what a builder says about its own work lands
  nothing. When the board is built, `factory-finish` runs the project's own gate
  commands once, refuses a suite that ran zero tests, compares the test census
  with the run's start, and runs the change's acceptance command. A red full check
  runs `factory-bisect` over the run's commits to name the first task that broke
  it.
- **A report from disk.** The closing report is built from where every task file
  is and which commit carries it, not from what the agents said - and what the
  builders flagged and left open (`## Open concerns`) comes first. It is also
  written to `.factory/last-run.md`, and the session gets one line back
  (`FINISH 6/6 landed; ...`).
- **Escalate, don't loop.** A red task gets a fresh builder at higher effort, up to
  `retry_limit` attempts in all; then it is blocked with the reason, and what
  depends on it is skipped. Two attempts that made no progress block it sooner.
- **Tasks in flight cannot fail each other.** When every error a check points at
  is in another task's unlanded files, the check waits for that work to land
  instead of blaming this task, and a blocked task's half-written work is parked
  out of the tree (`factory-block --unpark` brings it back).
- **Reviews where they pay.** Generated files (`linguist-generated` in
  `.gitattributes`, or `risk_exclude`) never trigger one. A task sent to review
  only by a risk path lands first and is reviewed alongside the run
  (`fast.risk_review: after`, the default), so nothing waits on it;
  `review: always`, or `fast.risk_review: before`, is reviewed before it lands.
  The reviewer's findings go through `factory-review-submit`, which keeps only
  what it can tie to the task's diff (see [3.4](#one-loop-34)); only P0 and P1
  block. A failed review before landing goes to a fresh builder with exactly those
  findings; one after landing holds the change's delivery.
- **An audit of the seams.** After the build, one auditor reads everything the
  run landed against the goal - data passed between tasks, flows nothing wires
  in, races, contracts - the defects no single task's check or review can see,
  and writes one audit per change to `.factory/audit/<change>.md`.
- **A graph built for speed.** `factory-plan` measures the longest dependency
  chain and warns before a run that is mostly one chain; `/factory:init` uses it
  to merge links and move serial work to the end, and writes a `## Context` for
  every task so a builder does not rediscover the codebase.
- **Measured, not guessed.** `factory-cost` reads the session's transcripts and
  shows requests, output and thinking tokens and an estimated cost per role.

Measured with factory 2.3 on the same six-task Flutter feature, same board, same
session model and effort, both runs finishing 6/6 with a green full check - the
lead-driven loop `/factory:run` was then, against the workflow that was
`/factory:fast`:

| | lead loop | workflow |
| --- | --- | --- |
| wall-clock | 14m13s | 5m03s |
| cost | $3.43 | $1.05 |
| model requests | 216 | 86 |
| output tokens (thinking included) | 77,460 | 30,290 |

That difference is why 3.4 removed the lead loop and made the workflow the only
one.

## Delivery (2.8)

A closed change can leave your machine, but only through one script and only as far as your consent goes. An agent still never pushes: `factory-publish` is a script outside the agent hooks, started by `factory-deliver` when a run's change is ready (and resumed by the next session if it was interrupted).

| Level (typed `auto devam et`) | What the publisher does |
| --- | --- |
| `local` | nothing - `PUBLISH SKIPPED` |
| `pr` | pushes `factory/<Cn>-<slug>` and opens the pull request, then stops (`pr_only`) |
| `merge` | also waits for CI, merges, watches main's CI, and reverts if main goes red |

- **Classes.** A: merged when green. B: touches a `risk_paths` glob, merged only when the change was reviewed before landing and no review failed. C: migrations, workflows, CODEOWNERS, CLAUDE.md, fastlane/release config, a major dependency bump - a pull request only, never merged by the factory.
- **Config** (`.factory/config.json`): `delivery.branch` (`main` keeps one branch, `per-change` cuts `factory/<Cn>-<slug>` from `origin/<base>`), `delivery.merge_method` (`rebase`, falling back to `squash` with the trailers in the body), `delivery.base`, `delivery.quota_margin`.
- **Merge is pinned** with `--match-head-commit` to the commit that was tested; a head that moved is held, not merged. Unacknowledged `## high` findings in `.factory/audit/<Cn>.md` hold the change: `factory-publish --ack-audit <Cn>`.
- **Breakers.** Two reverts in seven days, or two red mains in a row, write `.factory/autonomy-cap` and the level drops to `pr`. A hard-ban hit does the same. Only a new typed `auto devam et` clears it. Above the week's even-spend line plus `quota_margin`, no new builder starts at level `merge`.
- **See it.** `factory-publish --status`, the `delivery:` part of the band, and the morning digest in `.factory/digest/<date>.md` (`factory-digest --line`).
- **Needs** `gh` logged in on the machine (`gh auth login`); an auth error holds the change and resumes on the next call.
- The pull request, CI and revert flow was tested against a fake `gh` and a bare origin, never a live GitHub.

## Retrospective that learns (2.9)

`factory-finish` writes `.factory/retro-due` when 30 new failure signatures piled up or a week with runs passed; the session brief says `RETRO DUE`. With `retro.mode: suggest` (the default) nothing else happens: run `/factory:retro` and approve. With `retro.mode: full` a run ends with the `factory:retro` agent, and `factory-retro-apply` - never the agent - applies only what cannot loosen the gate: lessons with evidence, `gate_isolation`/`isolation_links`/`risk_paths` widening/`min_tests` raised/`retry_limit` lowered/`fast.risk_review: before`/`fast.audit` on, and one CLAUDE.md protocol rule per retro. Plugin changes are only listed. Every change is a commit with a `Factory-Retro: <date>/P<n>` trailer and a line in `.factory/retro/ledger.jsonl` with the metric's baseline; `factory-retro evaluate` takes back what did not move its metric after `retro.min_sample` tasks.

## Outer loop (3.0)

`factory-next check` answers `NEXT GO <change>` only when the autonomy level is `merge` (typed "auto devam et"), the quota file has a fresh reading under the even-spend line, no publish is in flight, no run is active and an approved change is waiting - otherwise `NEXT WAIT <why>`. `factory-next launch` then runs `claude -p "/factory:run <change>" --permission-mode auto --permission-prompts none --allowedTools "Workflow(factory:loop)" --strict-mcp-config` in a git worktree under `.factory/worktrees/` (your working tree is never touched). `factory-next launchd --hour 3` prints a LaunchAgent plist for a nightly run; nothing is installed for you. A breaker's cap, `auto dur` or `.factory/STOP` stops it. Opt-in: `check.modifies_tests_guard: true` fails a task that rewrites an assertion in an existing test unless `modifies_tests: true` was committed in its task file first.

## Rules that hold (3.2)

- **What was approved is what is judged.** When a run starts, `factory-preflight`
  commits the run's task files as they were approved (a `Factory-Board: snapshot`
  commit of task files only). From then on the check reads `acceptance` and the
  exemptions (`untested_ok`, `allow_test_removal`, `modifies_tests`, `dependencies`)
  from that commit, not from the working tree: an exemption a builder writes into its
  own task is ignored and named, and an acceptance rewritten mid-run is red. A task
  whose approval changed since its last commit is not committed as approved - the run
  does not start until you commit it or put it back - and a snapshot git refuses
  stops the run with git's reason. Only the run's own preflight records the start.
- **The gate cannot change under a run.** The run's start records a digest of
  `gates/` and `.factory/config.json` (its `hard_blocks` choices aside). Every check
  compares it, and a task that lists either is red.
- **Bans in every spelling.** The hard blocks read a path in every spelling
  (`C:\p\x`, `/c/p/x`, `$PWD/x`, `$(pwd)/x`, `~+/x`, `./x`, `a/../x`, any letter
  case) and a command in every quoting (`g''it "push"`, `bash -c 'git push'`). They
  judge PowerShell like bash, refuse a git command that rewrites the shared tree or
  index (`stash`, `reset`, `checkout`, `commit`, ...) but not its read-only forms
  (`git stash list`, `git config user.email`), hold the folders that keep protected
  files (`rm -rf .factory`, `cp -r x gates`), refuse a forged consent
  (`factory-consent`) and a lesson an agent writes, and protect the factory's own
  records (`.factory/verified`, the event log, questions, lessons). A tool the
  factory cannot judge is refused for a subagent.
- **Prose is not a command.** What a command only prints or searches for is not
  read as one: the quoted text of `factory-block`, `factory-ask`, `grep` or `echo`
  (`factory-block T5 'copy the key into .env'`), a heredoc `cat` writes to a file, a
  comment - so a blocked task's reason does not halt the run. Inline code that writes
  and names a protected path (`python -c`, `node -e`) is refused without halting it:
  that match is a guess. The judge is one algorithm in two languages (Python for the
  PreToolUse hook, JavaScript in the hooks module), held to one list of cases
  (`tests/hardblock-cases.txt`).
- **A dependency is declared, or the task is red.** Changing a dependency manifest
  (`package.json`, `requirements.txt`, `go.mod`, a `.csproj`, ...) is red unless the
  approved task file says `dependencies: [name]`; a new module named like a package
  (a local `requests.py`) or a write under `node_modules/` is red too. Manifests and
  lockfiles are also a risk path for review; `risk_builtin: false` turns that off.
- **A task that cannot be built as written is asked, not retried.** A builder
  settles it with `factory-settle --conflict "<the question>"`, which blocks the
  task and puts the question in your inbox. `factory-start` refuses a task whose dependency has not
  landed in HEAD.
- **One pointer in CLAUDE.md.** Every agent loads `CLAUDE.md` on every turn, so
  `/factory:init` writes a four-line pointer there and the rules stay in each agent's
  instructions. `/factory:upgrade` replaces the old 64-line protocol section.
- **Windows.** The suites and the hooks module run on Windows under Git Bash, and CI
  runs them on macOS, Linux and Windows.

## One gate (3.3)

- **One engine.** `factory-check` is the gate. A project's `gates/verify.sh` is a
  five-line shim that runs it (`exec factory-check "$@"`), and the project's own
  stages - a migration dry-run, a bundle-size budget - go in `gates/extra.sh`, which
  every check runs last with the task id (or `--full`). Both are under `gates/`, so
  no agent changes them. `factory-upgrade --apply` replaces a gate that is one of
  the templates `/factory:init` used to generate (backed up to
  `.factory/gate-legacy/`); a gate you wrote yourself is kept, and the upgrade says
  how to move its stages into `gates/extra.sh`. What only the template did now
  lives in the engine: `gate_mode: staged` (a stage without a command is skipped,
  one green stage is enough), a full check that refuses a missing build, test or
  lint command in full mode, test counts for Flutter's `+N` lines, and isolation
  that keeps `isolation_links` linked.
- **The tests the project has are read-only.** A subagent writes new tests, never
  an existing one: a write to a test file or to test infrastructure HEAD has
  (`conftest.py`, `jest.config.*`, `pytest.ini`, a CI workflow, ...) is refused
  without halting the run - by the PreToolUse hook and by the hooks module, in a
  file tool, a redirect, `sed -i`, `cp`, `rm`, `cd tests && ...` or inline code. An
  approved `modifies_tests` in the task file frees it: `true` for any test, or a
  list (`modifies_tests: [tests/api/*, conftest.py]`) for exactly those. A change to
  how the tests run (`scripts.test` in `package.json`, the pytest section of
  `pyproject.toml`, `setup.cfg` or `tox.ini`) is red unless that list covers it.
- **Cheat signatures.** The check reads the lines a task added for what makes a
  suite pass without the code working: an exit with success outside an entry point
  (`sys.exit(0)`, `os._exit`, `process.exit(0)`), a skip outside the tests, product
  code that reads the call stack or opens a test file, a patched test report
  (`pytest_runtest_makereport`, `TestReport`). These are red. Ambiguous ones - an
  `__eq__` that is always true, a patched test framework - are not: they go into
  the task's marker as `review=` lines, and `factory-risk` sends the task to a
  reviewer. `check.entry_points` (globs) and `check.cheat_allow` (`"rule"` or
  `"rule:glob"`) take a false hit out; `check.cheat_guard: false` turns the stage
  off.
- **HEAD's test, on the new code.** When a task was allowed to change a test HEAD
  has, the check also runs HEAD's version of that test against the task's code, in
  a throwaway worktree. If the old test fails, the task goes to review: whether the
  behaviour was meant to change is your call. `check.frozen_suite: false` turns it
  off.
- **What was checked is what lands.** The marker holds a digest of the task's listed
  files; `factory-land` computes it again and refuses a task whose files changed
  after its green check.
- **Shadow mode.** `tests/suite12.sh` runs the old template and the engine on the
  same fixtures and compares their verdicts. Every difference is listed with the
  reason the engine is right; one that is not listed fails the suite.

## One loop (3.4)

- **One way to build.** `/factory:run` makes two calls: `factory-preflight --json`,
  then the workflow `factory:loop` with the plan it printed. The model-driven lead
  loop is gone, and with it the lead, implementer and integrator agents, the Stop
  hook, the run claim, the agent-limit hook and the memo carried across a
  compaction. `/factory:fast` is the old name, kept for one release. `fast.workers`
  is how many builders work at once, and `factory-plan --ready` prints the ready
  set `factory-ready` used to.
- **The board is settled before anything starts.** `factory-preflight` stops on
  `.factory/STOP`, on the unpushed breaker, and on uncommitted work of yours above
  autonomy level `local`. It takes answered questions back into their tasks and
  returns them to the backlog, blocks a `needs_human` task or one that does not
  lint and asks you about it, commits the approved task files, and writes
  `.factory/run.lock`.
- **Scripts decide, from disk.** A builder's last command is `factory-settle`. It
  reads the check's marker, the risk paths, the attempts so far and what the task
  is waiting on, and prints what it did: `LANDED`, `REVIEW`, `WAITING`, `RETRY`,
  `BLOCKED`, `UNCOMMITTED`, `HALTED` or `REFUSED`. The workflow acts on that line,
  not on the builder's account of its work; a builder that did not settle is
  settled by a runner.
- **Review findings are filtered, not trusted.** A reviewer submits its findings as
  JSON to `factory-review-submit`. A finding under 80% confidence, one marked
  pre-existing, one about lint, style or the compiler, one in a file the task's
  diff does not touch, one whose quoted line the diff did not add, or one more than
  three lines from a changed hunk is dropped. Only P0 and P1 block. Each review is
  recorded in `.factory/reviews/<id>.json`.
- **A halted run keeps its base.** A quota limit, `.factory/STOP`, or an agent that
  returns nothing twice halts the run without blocking a task. `.factory/run.lock`
  is marked halted, and typing `/factory:run` again continues from the same base,
  so the full check and the report still cover the whole run.
- **Delivery waits for the whole picture.** `factory-deliver --if-ready` hands a
  change to the publisher only when its full check is green on the current HEAD
  with a clean tree, no review of its tasks failed or is still owed, and its audit
  is written with no unaccepted `high` finding (`factory-publish --ack-audit <Cn>`
  accepts them). Until then it says `DELIVER WAIT` or `DELIVER HELD`. The finish
  and the audit run side by side and both call it, so the one that ends last hands
  the change on.
- **One line back.** `factory-finish` prints one line (`FINISH 6/6 landed; ...`),
  and `--json` the whole result; the details are in `.factory/last-run.md`. A red
  full check runs `factory-bisect` over the run's commits and names the first bad
  task.
- **Headless.** `factory-next` launches `claude -p "/factory:run <change>"` with
  `--allowedTools "Workflow(factory:loop)"`. In any other headless session,
  `factory-preflight` warns when no settings file allows `Workflow(factory:loop)`.
- **The schedule is tested.** `tests/suite13.sh` runs the workflow under a fake
  `agent()`: dependencies, retries, waits, an empty answer, the stop race, reviews
  before and after landing, and the plan from args or from the preflight.

## The plan, and a night with nobody there (3.5)

- **The plan is checked before you approve it.** `/factory:init` writes the
  change's requirements, numbered, to `.factory/changes/<Cn>.requirements.md`
  (`- FR-001: ...`), asks at most five questions - each with the answer it
  recommends - and every task names what it builds in `covers: [FR-001]`.
  `factory-lint --plan <Cn>` fails a plan with a requirement no task builds, a
  task that covers none, a dependency cycle or a dependency on a task that does
  not exist, an open `[NEEDS CLARIFICATION]`, `TODO`, `TKTK` or `???`, a task
  past 8 acceptance criteria or 15 named paths (`plan.max_criteria`,
  `plan.max_files`), or an acceptance command that never exits (a watch mode, a
  dev server) or cannot fail (`true`, `... || true`). A change of three tasks or
  fewer fails only on a broken graph. The approval screen shows the verdict and
  a coverage table, and `factory-preflight` does not start a run on a FAIL.
- **Must-haves.** A task's `## Must haves` says what has to exist when it is
  done. `artifact: <path>` (there, and not empty) and `link: <path>: <text>`
  (wired in) are checked by `factory-musthaves` at the end of every run, and a
  miss is the first thing the report shows; a `truth:` is behaviour, for the
  auditor. The auditor starts from "every task is done and the goal is still
  missed" and classes each finding as missing, partial, contradicts or
  unrequested.
- **More is always reviewed.** Besides dependency manifests, `factory-risk`
  always sends these to a reviewer: the test harness configuration, the CI, the
  project's `gates/`, test doubles (`mocks/`, `__mocks__/`, `fakes/`, `stubs/`,
  `*.mock.*`) and migrations - a task can make its own tests pass by changing
  them - and any change larger than `review.max_lines` (400; `0` turns it off).
- **Standards by path.** A file `.factory/criteria/<area>.md` with
  `applies_to: [globs]` or `modules: [...]` in its frontmatter is printed by
  `factory-start` only to a builder whose task names a matching path, and read by
  the reviewer through `factory-criteria <id>`. A standard no task touches is in
  nobody's context.
- **A budget per builder.** A builder that loops is stopped. The hooks module
  counts each builder's model requests and tokens (`fast.budget`, default 150
  turns and 3,000,000 tokens of input, output and cache writes; `0` turns one
  limit off, `false` both). At 80% the builder is told to wrap up; at the
  ceiling every tool call is refused except settling, blocking or asking, so it
  writes what it tried, settles, and the task is retried at a higher effort or
  blocked. Reviewers, runners and your own session are never limited.
- **A start check.** With `check.start_full: auto`, `factory-preflight` runs
  `factory-check --full` at HEAD before the run unless the last full check was
  green at that commit, and a red tree does not start a run. `always` runs it
  every time; `off`, the default for a project set up before 3.5, skips it.
- **Nothing waits on a prompt.** `factory-next launch` adds
  `--permission-prompts none`: anything that would ask is refused, and the
  agent is told so. `factory-allow --apply` (run by `/factory:init` and
  `/factory:upgrade`) adds what a run needs to `permissions.allow`: the loop
  workflow, the factory's commands, read-only git and the project's build,
  test, lint and format commands, keeping your own rules. A headless preflight
  warns about any that are missing.
- **You are told, wherever you are.** `factory-notify` sends every new question,
  every breaker trip and every run's one line to the desktop (Notification
  Center on macOS, a toast on Windows, notify-send on Linux) and, with
  `notify.ntfy` set to an ntfy topic URL, to your phone. A question carries a
  deadline (`questions.deadline_hours`, 24) and may carry a default
  (`factory-ask ask <id> "<question>" --default "<answer>" --deadline 8h`): past
  the deadline the next preflight takes the default and the task goes on, or
  marks the question expired and the task stays blocked.
- **Windows nights.** `factory-next schtasks [--hour H] [--timeout-min M]`
  writes `.factory/schedule/next.ps1` and prints the `schtasks /Create` line
  that registers it (and the `/Delete` line). The wrapper starts nothing while
  `.factory/STOP` exists, takes a lock so two starts never overlap, stops a run
  that outlives the timeout (4 hours) with every process it started, and logs
  to `.factory/logs/`. Nothing is installed for you. On macOS it is
  `factory-next launchd`. A night run's worktree now gets the lessons and the
  criteria files too.

## Opt-in depth (3.6)

Every item here is off until you turn it on, and each one's outcomes are
counted per run in `.factory/metrics.jsonl` under `mechanisms` (what it caught,
what it cleared), so you can see what it is worth before you keep it.

- **Security scans.** `check.security` scans what each task adds: gitleaks (a
  secret is red) and semgrep against HEAD (`semgrep_config`; a finding goes to a
  reviewer, or is red with `semgrep_red: true`). `check.security.full` lists
  whole-tree scans (CodeQL, `npm audit`, `pip-audit`, ...) that run at the end of
  a run, with their reports in `.factory/scans/`. A tool that is not installed is
  skipped with a note.
- **Mutation testing.** `check.mutation` runs your mutation tool on the run's
  diff after a green full check (`{"command": "cargo mutants --in-diff {diff}"}`,
  or Stryker with `--mutate {files}`). A surviving mutant in changed code is
  never red: it is listed for you and for the auditor - a test that does not
  assert the behaviour it covers.
- **EARS criteria.** With `plan.ears: true`, `factory-lint --plan` lists every
  acceptance criterion not in EARS form ("The X shall ...", "When ..., the X
  shall ...", "While ...", "If ..., then the X shall ...", "Where ...") as a
  concern, never a failure.
- **Area leases.** With `fast.area_lease: true`, two tasks with the same `area:`
  in their frontmatter never build at the same time; a task with no area takes
  no lease.
- **A cheat monitor.** With `review.monitor: true`, a task whose green check found
  a cheat signature or a frozen suite does not land: one read-only monitor agent
  asks a single question - does this diff make the checks pass without doing
  what the task asks? - before the reviewer. A cheat verdict backed by evidence
  in the diff blocks the task and asks you; it is never handed back to a
  builder as something to fix until it passes. Verdicts are kept in
  `.factory/monitor/`.
- **A checkout per builder.** With `"fast": {"isolation": "worktree"}` each task
  builds in `.factory-worktrees/task-<id>`, a git worktree with the factory's
  files and `isolation_links`, so builders never see each other's half-written
  files. Settling merges the task's files into the project tree one task at a
  time and checks them again there; only that check lands the task. A conflict
  or a red there leaves the tree as it was and is a retry. Put what the build
  needs and git does not hold in `isolation_links`, and make a test runner that
  scans from the root skip `.factory-worktrees/`.
- **Merge queue.** With `delivery.merge_queue: true`, a green pull request at
  level merge goes to the base branch's merge queue instead of being merged by
  the publisher, so CI tests it on top of everything ahead of it. That needs a
  workflow that runs on `merge_group`; without one the publisher holds the
  change and says so. Turn the queue on in the base branch's ruleset first.
- **Spec ledger.** With `specs.ledger: true`, each change carries a `delta.md`
  (`## ADDED`, `## MODIFIED`, `## REMOVED`, as `- FR-NNN:` lines), seeded from
  its requirements and merged into `specs/requirements.md` when the change
  closes - all of it or nothing. `factory-change validate <Cn>` refuses a change
  with no delta unless it says `skip_specs: true`; `factory-change drift` lists
  requirements no test names. The ledger is left for you to commit.
- **Untrusted text is framed** (always on). An issue body, a page or a log a
  task quotes goes under `## Source: <where>` or `## Untrusted`; `factory-start`
  prints it inside an `<untrusted>` block, and builders read it as data, never
  as instructions. Only the approved task file and your answers instruct them.
- **A stuck check.** With `"fast": {"stuck": true}` (off by default) the hooks
  module watches each builder's calls. The same call with the same result 4
  times in a row, the same failing call 3 times, or two calls taking turns 6
  times (A B A B A B) is a builder going round in circles: the first time the
  call's result comes with a reminder to change the approach; the second time
  every call is refused except settling, blocking or asking, as at a full
  budget, and the builder settles the task as `no_progress`. Waiting and looking
  around never count: `sleep`, `wait`, `date`, `pwd`, `ls`, `git status`,
  `git log`, `git fetch` run on their own, and polling a background task. Each
  trip is a `stuck` line in `.factory/events.jsonl`.
- **Rules.** A lesson builders kept ignoring can become a rule:
  `.factory/rules/<name>.rule` (`match: bash|path|content`, a regex,
  `action: warn|block`, a message, the evidence). The hooks module holds every
  builder's call to it: `warn` lets the call run with the message attached,
  `block` refuses it and the run goes on. A rule never applies to the factory's
  own commands or the task files, so it can never stop a builder from checking
  or settling. Only `factory-retro-apply` writes one - two per retrospective,
  ten in all - and agents may not touch the folder (hard block
  `factory-rules`). Each hit is a `lesson_rule` line in the event log, and the
  retro digest shows how often each rule fired.
- **Lessons keep their shape.** A lesson may carry a `category` (`build`,
  `test`, `tooling`, `convention`, `environment`, `dependency`) and a
  `retire_when` (a path that must exist, or a commit HEAD must reach).
  `factory-lesson add` refuses a lesson that overlaps one already in the file
  and names the one to reword with `factory-lesson update <module> <n>`;
  `factory-lesson check` lists the lessons whose `retire_when` is gone, and the
  retro proposes retiring them. Lesson files written before keep working.

## Commands

| command | what it is for |
| --- | --- |
| `/factory:init` | set the factory up in a project: gate, board, task list, change |
| `/factory:run` | build the approved board: one preflight, then one builder, check and settle per task, one full check at the end |
| `/factory:fast` | the old name of `/factory:run`, kept for one release |
| `/factory:status` | the board, in detail, read-only |
| `/factory:dash` | open the live dashboard |
| `/factory:accept` | run a change's own acceptance command |
| `/factory:bisect` | find which task's commit broke a command |
| `/factory:retro` | what went wrong in this run, and what to change about the factory |
| `/factory:upgrade` | bring an older project's factory files up to date |
| `/factory:bans` | choose which optional bans (store/TestFlight tooling, git tags, GitHub releases) apply to this project |
| `/factory:selftest` | run the factory's own test suite |
| `/factory-board` | lane counts, what is ready and the week's quota, straight from disk: no model turn, so no tokens |

## The hooks module

Besides its command hooks, the plugin ships a [mod](https://code.claude.com/docs/en/plugins/mods/overview):
`hooks/register.js`, listed under `modules` in `hooks/hooks.json`. It needs Claude Code
2.1.287 or later (tested on 2.1.310). Nothing in it calls a model. Its hooks are of two
kinds, and the difference is the contract:

- **The hard blocks.** For a subagent of a factory run, `tool.call` judges every call
  against `hooks/hard-blocks.txt` - the same list the `PreToolUse` hook and the
  `permissions.deny` rules come from - and refuses what it forbids: a push, a rewrite
  of the work tree's git state, a write to `gates/`, the config, `.env*`, keys or the
  factory's own records, in any spelling of the path, through any shell or inline
  interpreter. A tool it cannot judge is refused too. This hook **fails closed**: if
  it cannot decide, the call is refused. A hit also writes `.factory/STOP`, which
  halts the run until you look. `agent.spawn` holds back a new agent when the week's
  quota is spent.
- **Observers.** Everything else - quota, usage metering, the board, the autonomy band -
  never refuses or rewrites anything, and a failure inside one is swallowed rather than
  allowed to stop a turn.

- **Quota.** Each rate-limit reading goes to `~/.claude/.factory-quota.json` — the
  5-hour and 7-day windows, and the line an even spend of the week would be at now.
  The status line below writes the same file; the mod also writes it in `claude -p`
  runs, where there is no status line.
- **Usage metering.** Every agent turn in a project with `.factory/active` adds one
  line to `.factory/usage.jsonl` (gitignored): the agent's id, type and label, the
  model, and its input, output, cache-read and cache-write tokens. This is what cost
  per task is computed from.
- **`/factory-board`.** The board read from disk and printed as is; it runs
  `factory-plan --ready` and costs no model turn.
- **Consent.** `auto devam et` / `auto dur`, typed by you as the whole prompt, is
  handed to `factory-consent`, which writes the autonomy record.

`claude --safe-mode`, `--bare` and `disableAllHooks` turn mods off. The hard blocks
then still stand in the `PreToolUse` hook and in `permissions.deny`; the gate itself
never relies on the mod.

## The status line

A plugin cannot install a status line for you, so this one is a file you point your
settings at. In `~/.claude/settings.json`:

Copy the script somewhere stable and point at that — a plugin's install directory
is versioned and moves on every update:

```bash
curl -fsSL https://raw.githubusercontent.com/yunusemrealpak/claude-factory/main/plugins/factory/statusline/factory-statusline.sh \
  -o ~/.claude/factory-statusline.sh
```

```json
{
  "statusLine": {
    "type": "command",
    "command": "bash ~/.claude/factory-statusline.sh",
    "refreshInterval": 30
  }
}
```

If you already have a status line you like, copy the block marked
`--- Factory segment ---` from
[`plugins/factory/statusline/factory-statusline.sh`](plugins/factory/statusline/factory-statusline.sh)
into it instead. It reads a cache the factory wrote and computes nothing, because a
status line blocks the UI while it runs.

## Updating

```bash
claude plugin marketplace update claude-factory
claude plugin update factory
```

The hooks, commands and agents update with the plugin. What does **not** update is
what `/factory:init` wrote into a project — `.factory/config.json`, the task layout,
and before 3.3 a full copy of the gate in `gates/verify.sh`. Every session tells you
when a project is behind, and `/factory:upgrade` brings the safe parts up to date. A
gate that is one of the old generated templates becomes the shim (the old file is
kept in `.factory/gate-legacy/`); a gate you edited is never rewritten.

## Safety

- An agent never pushes; a script publishes only when your autonomy level allows it. The only git writes in the loop are one commit per task and, when a run starts, one commit of the approved task files.
- The hooks are inert in a project with no `.factory/active`, so having the plugin
  enabled changes nothing anywhere else.
- No `--dangerously-skip-permissions`. Commands declare narrow `allowed-tools`.
- Agents never revive: one task, one fresh agent, closed when it returns.

## Development

```bash
claude --plugin-dir ./plugins/factory     # load it without installing
# with the plugin also installed, its bin/ shadows yours - put yours first:
PATH="$PWD/plugins/factory/bin:$PATH" claude --plugin-dir ./plugins/factory
bash plugins/factory/tests/run-all.sh     # the shell suites, sandboxes only
claude plugin validate --strict ./plugins/factory   # what Claude Code reads from the mod
(cd plugins/factory && claude plugin test)          # the mod's own tests, no session
```

The test suites build throwaway git repositories, boards and gates and run the real
hooks against them. They touch no project and remove their sandboxes afterwards.
