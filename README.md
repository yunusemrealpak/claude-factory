# Factory

A production line for Claude Code. You hand it a spec, approve the task list, and
it runs a board of agents that cannot mark work done until a gate proves it —
while a live dashboard tells you what the team is doing, what it is stuck on, and
what it needs from you.

```
🏭 C2-kasa-akisi 3/7 ▶2 ✋1 ⛔1 ⚠1
   change      done  agents questions blocked stalled
```

## Install

```bash
claude plugin marketplace add yunusemrealpak/claude-factory
claude plugin install factory@claude-factory
```

Then, in any project:

```
/factory:init <spec file, or a sentence describing the work>
```

It reads the codebase, proposes a task list and a quality gate, and waits for your
approval. Nothing is dispatched until you say yes. Then:

```
/factory:fast
```

That builds the approved board as a workflow: one builder and one deterministic
check per task, and one full check at the end. It is the measured default, at
about a third of the cost and time of `/factory:run`, the lead-driven loop that is
still there for when you want to steer task by task (see [the fast lane](#the-fast-lane)).

## What it actually does

**A board with one law.** Tasks live in `tasks/backlog|in-progress|blocked|done`.
A task reaches `done` only after `gates/verify.sh <id>` wrote its verified marker.
That law is enforced by a `PreToolUse` hook, not by asking an agent nicely: a move
without the marker is denied.

**A gate that is hard to fool.** The gate runs build, tests, architecture rules and
lint, and it also counts: a suite that ran zero tests is not green, a run with
fewer test files or more skip markers than the last green one is not green, and an
acceptance criterion whose only evidence is a sentence in a markdown file is
rejected outright. It fingerprints failures, so a task that fails twice on the
identical error is stopped rather than retried until its budget runs out.

**One commit per task, locally.** After the post-integration gate, the integrator
commits exactly the files the task listed, with `Factory-Task` and `Factory-Change`
trailers. An agent never pushes (a script publishes only when the autonomy level you consented to allows it), and your own uncommitted work is never swept in.
When every task of a change is done, the change is archived with a summary and a
local ref under `refs/factory/`.

**A team you can watch.** Hooks write an event log; from it, `.factory/dashboard.html`
shows what is running, what is struggling, what is waiting for you, how long tasks
take and what the session has cost. It costs zero model turns — every byte of it is
generated by shell scripts from files on disk.

**A way to ask you things.** When a task needs a decision only you can make, the
lead asks — with options and a recommendation — instead of going quiet in `blocked`.
The question lands on the dashboard and raises a desktop notification; the run
carries on with the rest of the board while it waits.

**Speed as a constraint.** Reviewers are dispatched on a red gate, on tasks marked
`review: always`, or when a task touches a path in `risk_paths` — never to confirm
a gate that is already green. The integrator skips its second gate run when the
tree is byte-identical to the one that passed. The ready set and the task lint are
scripts, not model reasoning.

## The fast lane

`/factory:fast` builds the same approved board without a model in the loop
between tasks. It is a Claude Code workflow: the dependency graph, the
scheduling, the retry and the review routing are plain JavaScript, so the only
model work left is writing each task's code.

Leave the run alone while it works. A Monitor or a poll on it wakes the main
session once per builder, and every wake-up re-reads that session's whole
context: on a 14-task run that was about a quarter of its cost. The workflow
reports once, at the end.

- **One builder per task.** It starts the task (`factory-start` prints the task
  and its lessons in one go), writes the code and the tests the task asks for,
  and does not run tests while it works.
- **One deterministic check.** `factory-check` formats the touched files, builds
  and lints, runs the tests of the units the change reaches - the parts the
  project is made of and their dependents, declared in the config - and runs
  the task's own acceptance command. It knows no language: every command comes
  from the project. It keeps every guard of the gate: marker, zero tests,
  self-certifying acceptance, NO PROGRESS, and a test census judged per task
  against HEAD, so tasks in flight cannot trip each other.
- **Land, then judge the whole once.** `factory-land` moves the task to done and
  commits it. When the board is built, `factory-finish` runs the project's own
  gate commands once, refuses a suite that ran zero tests, compares the test
  census with the run's start, and runs the change's acceptance command.
- **A report from disk.** The closing report is built from where every task file
  is and which commit carries it, not from what the agents said - and what the
  builders flagged and left open (`## Open concerns`) comes first. It is also
  written to `.factory/last-run.md`.
- **Escalate, don't loop.** A red task gets one fresh builder at higher effort;
  red again, it is blocked with the reason, and what depends on it is skipped.
- **Tasks in flight cannot fail each other.** When every error a check points at
  is in another task's unlanded files, the check waits for that work to land
  instead of blaming this task, and a blocked task's half-written work is parked
  out of the tree (`factory-block --unpark` brings it back).
- **Reviews where they pay.** Generated files (`linguist-generated` in
  `.gitattributes`, or `risk_exclude`) never trigger one. A task sent to review
  only by a risk path lands first and is reviewed alongside the run, so nothing
  waits on it; `review: always` is still reviewed before it lands.
- **An audit of the seams.** After the build, one auditor reads everything the
  run landed against the goal - data passed between tasks, flows nothing wires
  in, races, contracts - the defects no single task's check or review can see.
- **A graph built for speed.** `factory-plan` measures the longest dependency
  chain and warns before a run that is mostly one chain; `/factory:init` uses it
  to merge links and move serial work to the end, and writes a `## Context` for
  every task so a builder does not rediscover the codebase.
- **Measured, not guessed.** `factory-cost` reads the session's transcripts and
  shows requests, output and thinking tokens and an estimated cost per role.

Measured with factory 2.3 on the same six-task Flutter feature, same board, same
session model and effort, both runs finishing 6/6 with a green full check:

| | `/factory:run` | `/factory:fast` |
| --- | --- | --- |
| wall-clock | 14m13s | 5m03s |
| cost | $3.43 | $1.05 |
| model requests | 216 | 86 |
| output tokens (thinking included) | 77,460 | 30,290 |

`/factory:run` is still there and still works the way it did.

## Delivery (2.8)

A closed change can leave your machine, but only through one script and only as far as your consent goes. An agent still never pushes: `factory-publish` is a script outside the agent hooks, started when a run closes a change (and resumed by the next session if it was interrupted).

| Level (typed `auto devam et`) | What the publisher does |
| --- | --- |
| `local` | nothing - `PUBLISH SKIPPED` |
| `pr` | pushes `factory/<Cn>-<slug>` and opens the pull request, then stops (`pr_only`) |
| `merge` | also waits for CI, merges, watches main's CI, and reverts if main goes red |

- **Classes.** A: merged when green. B: touches a `risk_paths` glob, merged only when the change was reviewed before landing and no review failed. C: migrations, workflows, CODEOWNERS, CLAUDE.md, fastlane/release config, a major dependency bump - a pull request only, never merged by the factory.
- **Config** (`.factory/config.json`): `delivery.branch` (`main` keeps one branch, `per-change` cuts `factory/<Cn>-<slug>` from `origin/<base>`), `delivery.merge_method` (`rebase`, falling back to `squash` with the trailers in the body), `delivery.base`, `delivery.quota_margin`.
- **Merge is pinned** with `--match-head-commit` to the commit that was tested; a head that moved is held, not merged. Unacknowledged `## high` findings in `.factory/audit.md` hold the merge: `factory-publish --ack-audit <Cn>`.
- **Breakers.** Two reverts in seven days, or two red mains in a row, write `.factory/autonomy-cap` and the level drops to `pr`. A hard-ban hit does the same. Only a new typed `auto devam et` clears it. Above the week's even-spend line plus `quota_margin`, no new builder starts at level `merge`.
- **See it.** `factory-publish --status`, the `delivery:` part of the band, and the morning digest in `.factory/digest/<date>.md` (`factory-digest --line`).
- **Needs** `gh` logged in on the machine (`gh auth login`); an auth error holds the change and resumes on the next call.
- The pull request, CI and revert flow was tested against a fake `gh` and a bare origin, never a live GitHub.

## Retrospective that learns (2.9)

`factory-finish` writes `.factory/retro-due` when 30 new failure signatures piled up or a week with runs passed; the session brief says `RETRO DUE`. With `retro.mode: suggest` (the default) nothing else happens: run `/factory:retro` and approve. With `retro.mode: full` a run ends with the `factory:retro` agent, and `factory-retro-apply` - never the agent - applies only what cannot loosen the gate: lessons with evidence, `gate_isolation`/`isolation_links`/`risk_paths` widening/`min_tests` raised/`retry_limit` lowered/`fast.risk_review: before`/`fast.audit` on, and one CLAUDE.md protocol rule per retro. Plugin changes are only listed. Every change is a commit with a `Factory-Retro: <date>/P<n>` trailer and a line in `.factory/retro/ledger.jsonl` with the metric's baseline; `factory-retro evaluate` takes back what did not move its metric after `retro.min_sample` tasks.

## Outer loop (3.0)

`factory-next check` answers `NEXT GO <change>` only when the autonomy level is `merge` (typed "auto devam et"), the quota file has a fresh reading under the even-spend line, no publish is in flight, no run is active and an approved change is waiting - otherwise `NEXT WAIT <why>`. `factory-next launch` then runs `claude -p "/factory:fast" --permission-mode auto --strict-mcp-config` in a git worktree under `.factory/worktrees/` (your working tree is never touched). `factory-next launchd --hour 3` prints a LaunchAgent plist for a nightly run; nothing is installed for you. A breaker's cap, `auto dur` or `.factory/STOP` stops it. Opt-in: `check.modifies_tests_guard: true` fails a task that rewrites an assertion in an existing test unless `modifies_tests: true` was committed in its task file first.

## Rules that hold (3.2)

- **What was approved is what is judged.** When a run starts, `factory-plan --start`
  commits the run's task files as they were approved (a `Factory-Board: snapshot`
  commit of task files only). From then on the check reads `acceptance` and the
  exemptions (`untested_ok`, `allow_test_removal`, `modifies_tests`, `dependencies`)
  from that commit, not from the working tree: an exemption a builder writes into its
  own task is ignored and named, and an acceptance rewritten mid-run is red. A task
  whose approval changed since its last commit is not committed as approved - the run
  does not start until you commit it or put it back - and a snapshot git refuses
  stops the run with git's reason. Only the run's own runner records the start.
- **The gate cannot change under a run.** The run's start records a digest of
  `gates/` and `.factory/config.json` (its `hard_blocks` choices aside). Every check
  compares it, and a task that lists either is red.
- **Bans in every spelling.** The hard blocks read a path in every spelling
  (`C:\p\x`, `/c/p/x`, `$PWD/x`, `$(pwd)/x`, `~+/x`, `./x`, `a/../x`, any letter
  case) and a command in every quoting (`g''it "push"`, `bash -c 'git push'`). They
  judge PowerShell like bash, refuse a git command that rewrites the shared tree or
  index (`stash`, `reset`, `checkout`, `commit`, ...) but not its read-only forms
  (`git stash list`, `git config user.email`), hold the folders that keep protected
  files (`rm -rf .factory`, `cp -r x gates`), refuse a forged consent
  (`factory-consent`) and a lesson an agent writes, and protect the factory's own
  records (`.factory/verified`, the event log, questions, lessons). A tool the
  factory cannot judge is refused for a subagent.
- **Prose is not a command.** What a command only prints or searches for is not
  read as one: the quoted text of `factory-block`, `factory-ask`, `grep` or `echo`
  (`factory-block T5 'copy the key into .env'`), a heredoc `cat` writes to a file, a
  comment - so a blocked task's reason does not halt the run. Inline code that writes
  and names a protected path (`python -c`, `node -e`) is refused without halting it:
  that match is a guess. The judge is one algorithm in two languages (Python for the
  PreToolUse hook, JavaScript in the hooks module), held to one list of cases
  (`tests/hardblock-cases.txt`).
- **A dependency is declared, or the task is red.** Changing a dependency manifest
  (`package.json`, `requirements.txt`, `go.mod`, a `.csproj`, ...) is red unless the
  approved task file says `dependencies: [name]`; a new module named like a package
  (a local `requests.py`) or a write under `node_modules/` is red too. Manifests and
  lockfiles are also a risk path for review; `risk_builtin: false` turns that off.
- **A task that cannot be built as written is asked, not retried.** A builder returns
  `spec_conflict` with the one question; the run blocks the task and puts the
  question in your inbox. `factory-start` refuses a task whose dependency has not
  landed in HEAD.
- **One pointer in CLAUDE.md.** Every agent loads `CLAUDE.md` on every turn, so
  `/factory:init` writes a five-line pointer there and the rules stay in each agent's
  instructions. `/factory:upgrade` replaces the old 64-line protocol section.
- **Windows.** The suites and the hooks module run on Windows under Git Bash, and CI
  runs them on macOS, Linux and Windows.

## Commands

| command | what it is for |
| --- | --- |
| `/factory:init` | set the factory up in a project: gate, board, task list, change |
| `/factory:run` | run the loop until only blocked work remains |
| `/factory:fast` | build the board as a workflow: one builder and one check per task, one full check at the end |
| `/factory:status` | the board, in detail, read-only |
| `/factory:dash` | open the live dashboard |
| `/factory:accept` | run a change's own acceptance command |
| `/factory:bisect` | find which task's commit broke a command |
| `/factory:retro` | what went wrong in this run, and what to change about the factory |
| `/factory:upgrade` | bring an older project's factory files up to date |
| `/factory:bans` | choose which optional bans (store/TestFlight tooling, git tags, GitHub releases) apply to this project |
| `/factory:selftest` | run the factory's own test suite |
| `/factory-board` | lane counts, what is ready and the week's quota, straight from disk: no model turn, so no tokens |

## The hooks module

Besides its command hooks, the plugin ships a [mod](https://code.claude.com/docs/en/plugins/mods/overview):
`hooks/register.js`, listed under `modules` in `hooks/hooks.json`. It needs Claude Code
2.1.287 or later (tested on 2.1.310). Nothing in it calls a model. Its hooks are of two
kinds, and the difference is the contract:

- **The hard blocks.** For a subagent of a factory run, `tool.call` judges every call
  against `hooks/hard-blocks.txt` - the same list the `PreToolUse` hook and the
  `permissions.deny` rules come from - and refuses what it forbids: a push, a rewrite
  of the work tree's git state, a write to `gates/`, the config, `.env*`, keys or the
  factory's own records, in any spelling of the path, through any shell or inline
  interpreter. A tool it cannot judge is refused too. This hook **fails closed**: if
  it cannot decide, the call is refused. A hit also writes `.factory/STOP`, which
  halts the run until you look. `agent.spawn` holds back a new agent when the week's
  quota is spent.
- **Observers.** Everything else - quota, usage metering, the board, the autonomy band -
  never refuses or rewrites anything, and a failure inside one is swallowed rather than
  allowed to stop a turn.

- **Quota.** Each rate-limit reading goes to `~/.claude/.factory-quota.json` — the
  5-hour and 7-day windows, and the line an even spend of the week would be at now.
  The status line below writes the same file; the mod also writes it in `claude -p`
  runs, where there is no status line.
- **Usage metering.** Every agent turn in a project with `.factory/active` adds one
  line to `.factory/usage.jsonl` (gitignored): the agent's id, type and label, the
  model, and its input, output, cache-read and cache-write tokens. This is what cost
  per task is computed from.
- **`/factory-board`.** The board read from disk and printed as is; it runs
  `factory-ready` and costs no model turn.
- **Consent.** `auto devam et` / `auto dur`, typed by you as the whole prompt, is
  handed to `factory-consent`, which writes the autonomy record.

`claude --safe-mode`, `--bare` and `disableAllHooks` turn mods off. The hard blocks
then still stand in the `PreToolUse` hook and in `permissions.deny`; the gate itself
never relies on the mod.

## The status line

A plugin cannot install a status line for you, so this one is a file you point your
settings at. In `~/.claude/settings.json`:

Copy the script somewhere stable and point at that — a plugin's install directory
is versioned and moves on every update:

```bash
curl -fsSL https://raw.githubusercontent.com/yunusemrealpak/claude-factory/main/plugins/factory/statusline/factory-statusline.sh \
  -o ~/.claude/factory-statusline.sh
```

```json
{
  "statusLine": {
    "type": "command",
    "command": "bash ~/.claude/factory-statusline.sh",
    "refreshInterval": 30
  }
}
```

If you already have a status line you like, copy the block marked
`--- Factory segment ---` from
[`plugins/factory/statusline/factory-statusline.sh`](plugins/factory/statusline/factory-statusline.sh)
into it instead. It reads a cache the factory wrote and computes nothing, because a
status line blocks the UI while it runs.

## Updating

```bash
claude plugin marketplace update claude-factory
claude plugin update factory
```

The hooks, commands and agents update with the plugin. What does **not** update is
what `/factory:init` wrote into a project — `gates/verify.sh`, `.factory/config.json`,
the task layout. Every session tells you when a project is behind, and
`/factory:upgrade` brings the safe parts up to date; the gate itself is never
rewritten without you watching.

## Safety

- An agent never pushes; a script publishes only when your autonomy level allows it. The only git writes in the loop are one commit per task and, when a run starts, one commit of the approved task files.
- The hooks are inert in a project with no `.factory/active`, so having the plugin
  enabled changes nothing anywhere else.
- No `--dangerously-skip-permissions`. Commands declare narrow `allowed-tools`.
- Agents never revive: one task, one fresh agent, closed when it returns.

## Development

```bash
claude --plugin-dir ./plugins/factory     # load it without installing
# with the plugin also installed, its bin/ shadows yours - put yours first:
PATH="$PWD/plugins/factory/bin:$PATH" claude --plugin-dir ./plugins/factory
bash plugins/factory/tests/run-all.sh     # the shell suites, sandboxes only
claude plugin validate --strict ./plugins/factory   # what Claude Code reads from the mod
(cd plugins/factory && claude plugin test)          # the mod's own tests, no session
```

The test suites build throwaway git repositories, boards and gates and run the real
hooks against them. They touch no project and remove their sandboxes afterwards.
