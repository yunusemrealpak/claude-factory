# Factory

A production line for Claude Code. You hand it a spec, approve the task list, and
it runs a board of agents that cannot mark work done until a gate proves it —
while a live dashboard tells you what the team is doing, what it is stuck on, and
what it needs from you.

```
🏭 C2-kasa-akisi 3/7 ▶2 ✋1 ⛔1 ⚠1
   change      done  agents questions blocked stalled
```

## Install

```bash
claude plugin marketplace add yunusemrealpak/claude-factory
claude plugin install factory@claude-factory
```

Then, in any project:

```
/factory:init <spec file, or a sentence describing the work>
```

It reads the codebase, proposes a task list and a quality gate, and waits for your
approval. Nothing is dispatched until you say yes. Then:

```
/factory:run
```

## What it actually does

**A board with one law.** Tasks live in `tasks/backlog|in-progress|blocked|done`.
A task reaches `done` only after `gates/verify.sh <id>` wrote its verified marker.
That law is enforced by a `PreToolUse` hook, not by asking an agent nicely: a move
without the marker is denied.

**A gate that is hard to fool.** The gate runs build, tests, architecture rules and
lint, and it also counts: a suite that ran zero tests is not green, a run with
fewer test files or more skip markers than the last green one is not green, and an
acceptance criterion whose only evidence is a sentence in a markdown file is
rejected outright. It fingerprints failures, so a task that fails twice on the
identical error is stopped rather than retried until its budget runs out.

**One commit per task, locally.** After the post-integration gate, the integrator
commits exactly the files the task listed, with `Factory-Task` and `Factory-Change`
trailers. Nothing is ever pushed, and your own uncommitted work is never swept in.
When every task of a change is done, the change is archived with a summary and a
local ref under `refs/factory/`.

**A team you can watch.** Hooks write an event log; from it, `.factory/dashboard.html`
shows what is running, what is struggling, what is waiting for you, how long tasks
take and what the session has cost. It costs zero model turns — every byte of it is
generated by shell scripts from files on disk.

**A way to ask you things.** When a task needs a decision only you can make, the
lead asks — with options and a recommendation — instead of going quiet in `blocked`.
The question lands on the dashboard and raises a desktop notification; the run
carries on with the rest of the board while it waits.

**Speed as a constraint.** Reviewers are dispatched on a red gate, on tasks marked
`review: always`, or when a task touches a path in `risk_paths` — never to confirm
a gate that is already green. The integrator skips its second gate run when the
tree is byte-identical to the one that passed. The ready set and the task lint are
scripts, not model reasoning.

## The fast lane

`/factory:fast` builds the same approved board without a model in the loop
between tasks. It is a Claude Code workflow: the dependency graph, the
scheduling, the retry and the review routing are plain JavaScript, so the only
model work left is writing each task's code.

- **One builder per task.** It starts the task (`factory-start` prints the task
  and its lessons in one go), writes the code and the tests the task asks for,
  and does not run tests while it works.
- **One deterministic check.** `factory-check` formats the touched files in place,
  analyzes them and everything that imports them, runs only the tests that reach
  the change through the import graph - bundled into one entrypoint - and runs
  the task's own acceptance command. Seconds, not minutes, and it keeps every
  guard of the gate: marker, census, zero tests, self-certifying acceptance,
  NO PROGRESS.
- **Land, then judge the whole once.** `factory-land` moves the task to done and
  commits it. When the board is built, `factory-finish` runs the full check and
  the change's acceptance command once.
- **Escalate, don't loop.** A red task gets one fresh builder at higher effort;
  red again, it is blocked with the reason, and what depends on it is skipped.
- **Measured, not guessed.** `factory-cost` reads the session's transcripts and
  shows requests, output and thinking tokens and an estimated cost per role.

Measured on the same six-task Flutter feature, same board, same session model and
effort, both runs finishing 6/6 with a green full check:

| | `/factory:run` | `/factory:fast` |
| --- | --- | --- |
| wall-clock | 14m13s | 5m03s |
| cost | $3.43 | $1.05 |
| model requests | 216 | 86 |
| output tokens (thinking included) | 77,460 | 30,290 |

`/factory:run` is still there and still works the way it did.

## Commands

| command | what it is for |
| --- | --- |
| `/factory:init` | set the factory up in a project: gate, board, task list, change |
| `/factory:run` | run the loop until only blocked work remains |
| `/factory:fast` | build the board as a workflow: one builder and one check per task, one full check at the end |
| `/factory:status` | the board, in detail, read-only |
| `/factory:dash` | open the live dashboard |
| `/factory:accept` | run a change's own acceptance command |
| `/factory:bisect` | find which task's commit broke a command |
| `/factory:retro` | what went wrong in this run, and what to change about the factory |
| `/factory:upgrade` | bring an older project's factory files up to date |
| `/factory:selftest` | run the factory's own test suite |

## The status line

A plugin cannot install a status line for you, so this one is a file you point your
settings at. In `~/.claude/settings.json`:

Copy the script somewhere stable and point at that — a plugin's install directory
is versioned and moves on every update:

```bash
curl -fsSL https://raw.githubusercontent.com/yunusemrealpak/claude-factory/main/plugins/factory/statusline/factory-statusline.sh \
  -o ~/.claude/factory-statusline.sh
```

```json
{
  "statusLine": {
    "type": "command",
    "command": "bash ~/.claude/factory-statusline.sh",
    "refreshInterval": 30
  }
}
```

If you already have a status line you like, copy the block marked
`--- Factory segment ---` from
[`plugins/factory/statusline/factory-statusline.sh`](plugins/factory/statusline/factory-statusline.sh)
into it instead. It reads a cache the factory wrote and computes nothing, because a
status line blocks the UI while it runs.

## Updating

```bash
claude plugin marketplace update claude-factory
claude plugin update factory
```

The hooks, commands and agents update with the plugin. What does **not** update is
what `/factory:init` wrote into a project — `gates/verify.sh`, `.factory/config.json`,
the task layout. Every session tells you when a project is behind, and
`/factory:upgrade` brings the safe parts up to date; the gate itself is never
rewritten without you watching.

## Safety

- Nothing is pushed, ever. The only git write in the loop is one commit per task.
- The hooks are inert in a project with no `.factory/active`, so having the plugin
  enabled changes nothing anywhere else.
- No `--dangerously-skip-permissions`. Commands declare narrow `allowed-tools`.
- Agents never revive: one task, one fresh agent, closed when it returns.

## Development

```bash
claude --plugin-dir ./plugins/factory     # load it without installing
bash plugins/factory/tests/run-all.sh     # 369 tests, sandboxes only
claude plugin validate ./plugins/factory
```

The test suites build throwaway git repositories, boards and gates and run the real
hooks against them. They touch no project and remove their sandboxes afterwards.
